staging area --> local repo (.git folder) --> remote repo (by default, represented by 'origin')

git commit -am 'message' ==> to both add and commit in single step

git commit --amend -m 'New commit message' ==> to modify the commit message that was wrongly typed before
git add . -> git commit --no-edit ==> to add a file to the last commit; useful when we missed to stage a file in the last commit and don't want to create one more new commit


git checkout <file> - to discard local changes to a file and restore to the version of the file till the last commit

restore vs reset vs revert:
---------------------------
git restore - primarily used to unstage a file that is added to the staging area
usage: git restore --staged <file_name> ==> By default, the git restore command will discard any local, uncommitted changes in the corresponding files and thereby restore their last committed state. With the --staged option, however, the file will only be removed from the Staging Area - but its actual modifications will remain untouched.

git restore --source HEAD~2 <file_name> (restore the file to 2nd last commit version from current HEAD; but this will remove the local changes done recently to that file)

git reset - can be used to unstage, but primarily used to remove a commit that was wrongly done and move back to an older commit
	--soft - this will ensure the commit is removed, but the changes done locally will be retained
	--hard - this will ensure the commit is removed, and also the changes done locally are lost
	-- in both cases, the HEAD is moved to the older commit mentioned in git reset command
usage: git reset HEAD~3 (move to 3rd last commit from current HEAD) - by default, --soft
git reset --hard HEAD~3 (this is a combination of git reset --soft HEAD~3 + git restore .)
	
git revert - similar to git reset, git revert is also used to move to an older commit, but the difference is, the older commit is created as a new commit and the HEAD will point to this new commit; this ensures commit history is retained

c1 -> c2 -> c3 -> c4 -> c5 (HEAD)
git reset c3 ==> c1 -> c2 -> c3 (HEAD) ==> here c4 and c5 are lost

c1 -> c2 -> c3 -> c4 -> c5 (HEAD)
git revert c3 ==> c1 -> c2 -> c3 -> c4 -> c5 -> c'3 (HEAD) ==> here HEAD will point to a new commit c'3 which is a copy of c3; also c4 and c5 commits are retained in the history

Note: HEAD is a pointer to the most recent commit, so it can be used as a reference point to move back to older commits

Cherry pick commits:
--------------------
- Checkout to the branch where the commit to be cherry picked exists; copy the commit hash to be cherry picked
- Checkout to the main branch or whichever branch where the commit needs to be added
- git cherry-pick <commit_hash>

Tags:
-----
- Bookmark on a commit; Mainly used to mark a release
Usage: git tag v1.0
git tag -a v2.0 -m "Release 2"
git push origin <tag_name>

git show <tag_name> ==> displays details about a tag like which commit it is pointing to

git checkout <tag_name> ==> Moves HEAD to a "detached HEAD" state -> create a new branch out of it
